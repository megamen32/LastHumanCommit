# Worktree, PR и единая история

## В начале работы

Определи основной checkout по Git (`git worktree list --porcelain`), а не по cwd
чата. Проверь через Herder другие сессии **этого репозитория**, включая его worktree.
При другом потенциальном писателе используй отдельный worktree. Повторно используй
уже назначенное дерево; если его нет:

```sh
python3 <LHC>/common/tools/lhc_worktree.py create --repo <project> --task <slug> --base origin/main
```

Ветка: `lhc/<slug>`, каталог: `<основной-корень>/.worktrees/<slug>`. При недоступном
Herder проверь файловый чат и текущее дерево; неизвестный владелец — причина
изолироваться, не остановить всё и не присвоить чужие изменения.
Одиночная сессия может оставаться в основном checkout. Если сосед появился позже,
перенеси только собственную отделимую работу в worktree, согласовав реальную коллизию.

## Пока выполняется задача

Сообщи область работ одним сообщением. Сохраняй готовые логические шаги коммитами.
Проверяй изменения коллег, когда они влияют на твой код, а не перед каждым действием.
Данные чата и временные результаты не заменяют исходники и не требуют отдельных
коммитов. Общий чат расположен в основном checkout даже для нескольких worktree.

Конфликт блокирует свою операцию. Доступные исследования, код и проверки выполняются
сразу; возвращайся к отложенному после них. Владелец чужого WIP продолжает свою работу.
Возраст файла и пропажа сессии из списка не передают права на его изменения.

## Публикация каждого участника

Перед push сделай fetch и сверь актуальную основную ветку. Влей её в рабочую ветку,
разреши смысловые конфликты, выполни затронутые проверки, затем push и PR.
Review и CI проверяют текущую голову PR. При наличии прав и зелёных проверок
влей PR; иначе оставь точную причину и продолжай доступную часть работы.
Используй native Git и `gh`/провайдер PR, а не отдельный менеджер Git поверх них.

Если push отклонён из-за новых коммитов, это не повод начинать новую задачу:
fetch, merge, проверка и повторный push. Force-push и удаление чужого кода не нужны.
После merge проверь уже объединённую основную ветку; новая интеграционная ошибка
исправляется новым проверенным изменением с сохранением истории.

Одиночная сессия в основном checkout тоже сверяет удалённую ветку, включает новые
изменения, проверяет и делает push. Ветка с изменением публикуется через PR, когда
PR применим; отсутствие отдельного worktree не отменяет требований к итогу.

## Завершение Full-цикла

Цель — одна достижимая опубликованная история и зелёный объединённый результат.
Разбери все относящиеся к циклу изменения, в том числе готовую работу коллег,
генерируемые файлы и nested repositories. Сначала публикуются коммиты вложенного
репозитория, затем его указатель. Чистота одной своей ветки не доказывает этот итог.

Активные владельцы заканчивают свои части. Финальную сверку делает интегратор или
последняя активная сессия: fetch, включение новых коммитов, проверка общей версии,
push и реальный пользовательский сценарий. Готовые части публикуются **до** ожидания,
чтобы участники не ожидали друг друга по кругу. Для оставшейся зависимости запиши
`resume_after`; полезная независимая работа продолжается до её исчерпания.

Full завершён после сведения относящихся к нему PR/коммитов, чистых деревьев его
участников и зелёного результата. Независимая будущая задача другого проекта
не расширяет этот цикл. При настоящем внешнем блокере сохрани PR и нужное действие,
не выдавая частичную публикацию за Full.

После подтверждённого включения в remote main удали только собственные чистые
неактивные worktree/ветки. Чужой WIP, unmerged branches и исходную работу сохраняй.
