# Снижение нагрузки действующего зеркала

Работающие сервисы server-100: `lhc-plan-mirror.service` и `lhc-plan-observer.service`. Конфигурация, права, источники, public URL и интервал обнаружения обычных изменений сохранены. Ограничения CPU/RAM/I/O не вводились.

Причины: observer каждую секунду заново регистрировал планы, читал все листья и полные локальные снимки; подтверждённые снимки повторно отправлялись каждые 30 секунд. Сервер перечитывал весь набор историй при запросах статуса и каталога, а каталог повторял это чтение через legacy(). В серверных JSON на момент диагностики было 10.492 МиБ.

Изменения:

- Stat-сигнатуры перед полным fingerprint, кеш служебных данных и регистрации; discovery новых планов до 5 секунд. При изменении обычного файла fingerprint обновляется сразу в существующем цикле.
- Подтверждённая пара identity+seq сохраняет факт доставки при перезапуске и больше не отправляется заново. Повторная одинаковая ошибка не переписывает тот же файл.
- Сервер использует неизменившиеся JSON и заголовки legacy из памяти. ETA и stalled считаются по текущему времени, при приёме данных ownership/CAS читаются заново под блокировкой.
- Контрольное перечитывание кешей через 30 секунд защищает от реально воспроизведённого same-size сохранения с совпавшими stat timestamps. Это не увеличение обычного polling interval.

Два 35-секундных окна `/proc/PID/stat` и `/proc/PID/io` отражают текущую рабочую нагрузку. Подробности в `measurements.json`; после установки окно независимо снял cost_guidance. Суммарно CPU 52.234% → 6.5935% одного ядра, файловое чтение 32.38504 → 2.07557 МиБ/с, физическая запись 0.41733 → 0.01416 МиБ/с (примерно 427 → 14.5 КиБ/с). Чтение rchar включает файловый кеш; физическое чтение в замерах было близко к нулю и не выдаётся за rchar.
