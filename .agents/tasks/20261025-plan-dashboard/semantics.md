# Смысл ожидаемых результатов плана

Исходное поручение: устранить противоречие между будущим осязаемым результатом и уже достигнутым фактом. Область — канонические документы и шаблоны; runtime, HTML, схемы и генерация принадлежат UI-исполнителю.

До правки PLAN_REPORT.md и plan-artifacts требуют результат, доступный «уже сейчас». После правки новый план объясняет, что будет работать и как тестировщик это проверит; текущие факты и доказательства показываются отдельно. Исторические отчёты сохраняются.

План одного листа, без делегирования: проверить определения → исправить противоречия и шаблоны → выполнить узкую проверку документов → закоммитить только свои пути и передать результат. Исходная оценка: 15 активных минут; фактическое активное время не измерено.

Рабочее решение — единый контракт в PLAN_REPORT.md и ссылки из ролей. Идеал — одинаковый смысл в документах и UI. Минимальная полезная реализация этого листа — определения, примеры, сценарии и новые шаблоны; UI выполняется отдельным назначенным исполнителем.

## Контракт для UI

- `goal`: «Цель» — зачем пользователь затеял изменения.
- `business_result` / `business_results`: «Что будет работать» — будущие наблюдаемые возможности пользователя после изменений. Имена полей сохраняются.
- `acceptance_scenarios`: необязательный `list[str]`, подпись «Как проверим»; каждая строка содержит участника/контекст, действия и ожидаемый видимый итог.
- `current_progress`: «Что уже сделано» — текущие факты с честными пределами проверки. Доказательства (`evidence`) подтверждают наблюдения, а не заменяют ожидаемую возможность.
- Старый заголовок «Бизнес-результат» принимается. Старые поля загружаются как исторические декларации; их наличие не доказывает выполнения.

## Пример для автора и тестировщика

Ожидаемый результат: «Пользователь сохранит локальный лист; в течение установленного интервала новая заметка появится по прежней ссылке, даже после восстановления сервера».

Сценарий: «Открыть страницу, изменить note обычным сохранением, дождаться обновления без publish; остановить только viewer в разрешённом fixture, сохранить офлайн, восстановить, проверить доставку».

«Сделан коммит», «выложен JSON», «123 tests passed» — сведения о работе и её проверке, а не ожидаемая пользовательская возможность. Для CLI/библиотеки пользователь — оператор/вызывающий код: описываются реальный вызов и наблюдаемый результат.
