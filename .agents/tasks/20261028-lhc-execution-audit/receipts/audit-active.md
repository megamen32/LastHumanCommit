## Пределы доказательств

- Все пять сессий из выборки выполнялись на `roomhacker-server-100`. Нет доказанной активной сессии со второго host. В общем снимке MacBook был `stale` с наблюдением от 26 октября; неполные/неперечисляемые harness coverage также отмечены для части флота. Поэтому вывод относится только к локальной выборке, не к флоту целиком.
- Для Agent Herder и CRM `fleet_session_view` вернул `fleet_session_read_unavailable`; цели/статус подтверждались ответами `agent_info` и локальными rollout-файлами. Для остальных использовались доступные native message tails и локальные rollout-файлы. Активность — моментальный признак Herder, а не гарантия продолжения работы.
- Не исследовались исходники/диффы сессий и runtime установка LHC. Это аудит conversational exposure, типовых task paths и результатов, видимых в этих источниках; не полный release audit.

## Минимальная рекомендация Lead по hook

Semantic intake без side effects уместен и адресует подтверждённый XERJ-пропуск, если он вызывается существующим LHC entry до первой реализации. Результат должен явно классифицировать `engineering → create/update and activate a plan`, `status/research/explicit opt-out → no plan`; продолжением считать только явно привязанный к текущей session план, а прочие планы показывать лишь как candidates. Не нужны prompt regex, Stop veto или новый scheduler.

Сам текст intake **не является жёсткой гарантией**, если hook опционален или его вывод не появляется в обычном entry path. Минимальный дополнительный шаг — подключить этот side-effect-free вызов к существующему обязательному LHC entry для engineering work и привести описания/триггеры skills в соответствие с уже действующим правилом. Сейчас правило расходится: `native/codex/AGENTS.md` и `skills/plan-artifacts/SKILL.md` требуют план для каждой авторизованной разработки, включая quickfix; descriptions `last-human-commit`/`plan-artifacts` сильнее акцентируют явную просьбу «сделать план». Такое подключение достаточно, чтобы устранить наблюдённый silent no-plan trigger gap, но без runtime проверки можно утверждать только наличие и согласованность prompt-пути, не автоматическое исполнение.
