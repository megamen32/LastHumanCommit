# Аудит контракта активации и исполнения плана

## Установленный результат

Проверены canonical checkout на `main` и установленный пакет `last-human-commit/1.6.1`. `cmp` подтвердил побайтное совпадение `src/common/tools/lhc_entry.py` с установленным `common/tools/lhc_entry.py`, а также Codex hook manifest, `last-human-commit` skill и `AGENTS.md`. Это подтверждает равенство этих source/package файлов, но не доказывает, что живой app-server внедрил hook в текущую сессию.

Установленный `--plan-entry` вызван в изолированном пустом Git-репозитории с обычным prompt `Fix a function in this repository`: exit 0, пустые stdout и stderr, файлов плана нет. Это проверка реального установленного обработчика, не реального пользовательского Codex turn.

## Три подтверждённых разрыва

1. **Нет плана — нет стартового шага.** Контракт требует план до реализации каждой разрешённой инженерной задачи ([`plugins/last-human-commit/AGENTS.md:94-101`](../../../plugins/last-human-commit/AGENTS.md)). Но [`src/common/tools/lhc_entry.py:46-67`](../../../src/common/tools/lhc_entry.py) ищет только готовые `queued`/`running` листья и возвращает `None`, если их нет; вызывающий путь в [`src/common/tools/lhc_entry.py:310-335`](../../../src/common/tools/lhc_entry.py) при этом штатно заканчивается без вывода. Сценарий закреплён в [`tests/test_native_instruction_hooks.py:56-60`](../../../tests/test_native_instruction_hooks.py). Минимальный итог: новый обычный инженерный prompt может перейти к работе без артефакта плана.

2. **Найденный открытый план может быть не про запрос.** Поиск в [`src/common/tools/lhc_entry.py:33-60`](../../../src/common/tools/lhc_entry.py) не читает prompt и выбирает открытый план для репозитория, предпочитая лист, где совпала сессия, иначе сортируя пути. Тест подаёт prompt `thanks` и получает незавершённый лист ([`tests/test_native_instruction_hooks.py:56-67`](../../../tests/test_native_instruction_hooks.py)). Дальше хук без проверки смысла просит продолжать найденный план и не создавать дубликат ([`src/common/tools/lhc_entry.py:325-334`](../../../src/common/tools/lhc_entry.py)).

3. **План не привязывается к исполнению, хотя документация это обещает.** Сам entry-код говорит, что не меняет состояние и оставляет выбор листа агенту ([`src/common/tools/lhc_entry.py:26-32`](../../../src/common/tools/lhc_entry.py)); фактический вывод лишь перечисляет ID листьев. Однако [`src/common/skills/plan-artifacts/SKILL.md:468-477`](../../../src/common/skills/plan-artifacts/SKILL.md) обещает автоматические binding, назначение session/owner, событие прогресса и создание scaffold при отсутствии плана. Эти действия в `lhc_entry.py` не выполняются. Плановый лист потому остаётся `queued`, пока Lead явно не запустит отдельную операцию.

## Инъекция и runtime

Установленный `.codex-plugin/plugin.json` указывает на `com.openai/hooks/hooks.json`, где есть `UserPromptSubmit` с `--plan-entry`. Общие `hooks/hooks.json` и ZCode hook manifest включают только запуск инструкций на старте/компактации и временной observer на `PostToolUse`; они не создают план на submit. `SessionStart` путь выводит только указатель прочитать `AGENTS.md` ([`src/common/tools/lhc_entry.py:336-345`](../../../src/common/tools/lhc_entry.py)). Поэтому источник и установленный пакет подтверждают регистрацию, но здесь не было независимого доказательства фактического hook injection в живую пользовательскую сессию. Не считать наличие манифеста или вывода CLI доказательством runtime-инъекции.

Инвентарь Agent Herder на момент проверки показал 24 активные сессии, но coverage был `partial`, 17 сессий имели неизвестный workspace, а точного workspace для этого checkout среди известных не было. Поэтому отсутствие другой активной работы в checkout не доказано. Канонический checkout был на `main` с уже существующими чужими изменениями; они сохранены. `.agents/PROJECT.md` в checkout не найден. Branch target для этой задачи — `main` по явному решению Lead, а не по найденному project-файлу.

## Минимальный маршрут исправления

Не добавлять классификатор языка запроса и не блокировать `Stop`. Семантическое решение о разработке, read-only запросе и продолжении конкретной задачи оставляет Lead. Вызов начала разработки должен использовать это решение как структурированный вход: либо создать один краткий quickfix-лист, либо явно выбрать связанный существующий план; при нескольких правдоподобных планах показать Lead один короткий выбор. После явного выбора использовать существующую локальную операцию активации листа (`lhc_plan_json.py activate`) с реальным session ID, не угадывать ownership по сортировке каталогов. Убрать из skill ложное обещание, что `UserPromptSubmit` сам создаёт/привязывает план, либо реализовать это поведение на заявленном пути.

Регрессии для L02: новый инженерный запрос без плана; обычный запрос при наличии несвязанного открытого плана; явное продолжение существующего плана; read-only/status prompt. Затем L03 отдельно подтверждает source/check, установленную копию и реальный Luna canary. Это исследовательский receipt; исправления кода здесь не выполнялись.
