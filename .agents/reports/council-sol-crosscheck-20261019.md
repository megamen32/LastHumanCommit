## Принятые аргументы

* **Ordered ledger лучше одного общего флага canary.** Принимаю MiniMax §2C,§7: сохранять применимые стадии и их порядок в existing outcome. У моего B стадии уже есть; уточнение MiniMax полезно тем, что явно предотвращает «consumer работает → можно забыть final PR». Per-type defaults уменьшают церемонию, но не переопределяют прямое поручение. Нужны canary и evidence каждой действительно обязательной стадии, не всегда шесть строк.
* **N/A только для неприменимого; blocked остаётся pending.** Принимаю §5.2–3: отсутствие прогресса останавливает автоматические повторы, а не превращает задолженность в complete. Не нужен cron и бесконечное пробуждение.
* **Raw rereadability — обязательная база provenance.** Принимаю §3 как необходимое условие: raw tool/CI/native transcript должен быть доступен для проверки, а авторская сводка его не заменяет. Независимый reviewer читает существующий raw источник; новый certificate/evidence store не нужен.
* **CI staging push — узкое исключение, не finish.** Принимаю §7: branch+commit+конкретная техническая необходимость, затем CI/preview и consumer; финальные PR/merge obligations сохраняются. Исключение не разрешает чужой/protected main.

## Отвергнутые или исправленные положения

**1. Rereadability недостаточна для canary.** В §3 правило «artifact существует и перечитывается» допускает подлинный raw stdout команды `printf 'HTTP 200 total=0'`: артефакт produced by run и rereadable, а `/totals` не вызван. Даже настоящий `curl /health` не проверяет checkout. Минимальный discriminator — соответствие **исполненной операции, target/revision и наблюдаемого expected result** исходному canary. Малый evaluator проверяет структуру/источник; существующий предметный review проверяет этот смысл по raw evidence. Не требую автоматического универсального semantic parser или нового reviewer на каждый receipt. `lhc_time_guard.py:761–828` уже фиксирует лишь returned/running/failed; `REVIEW_TO_DELIVERY.md:69–75` прямо запрещает считать вызов доказательством результата. Один review может закрыть несколько действительно покрытых стадий.

**2. Defaults/N/A не могут стереть требуемый merge.** MiniMax §8 корректен для прямо заданного Airlock PR-only, но «любой external repo → merge=N/A» слишком широко. Если пользователь требует и разрешает LHC merge, нет доступа — это **applicable+blocked**, а не N/A; снять обязанность может явное изменение scope. Если пользователь запрещает Airlock main — это неприменимая/запрещённая операция, не долг «получить права и всё-таки merge». Источник границы — `.agents/tasks/lhc-outcome-contract-20261019.md:13`, не GitHub admin role и не авторская однострочная override. Не принимаю MiniMax R1 «частые ошибки классификации → автоматически stronger set»: для явного read-only testing это заставит запрещённые code/deploy. Исправлять распознавание scope, а не повышать полномочия.

**3. Existing one-shot недостаточен после полезного прогресса.** MiniMax §5.1 «один continuation на obligation set» сохраняет исходный баг: набор обязательств прежний, но исправлена поверхность и нужен retest. В `lhc_entry.py:206–211` флаг `continuation_requested` остаётся true; `lhc_milestone.py:216–219` меняет surface_key и не снимает этот флаг. Нужна одна continuation на **новую relevant progress identity** внутри той же задолженности. Duplicate Stop/poll, другой call ID, чужой README и A→B→A не являются новым прогрессом. Relevant repair, завершение известного job или canonical human answer могут изменить следующий шаг без изменения набора стадий. HumanStop/UNKNOWN не переигрываются. Это ограниченное расширение existing state, не новый controller.

**4. `human_request_create` не создаёт карточку.** Утверждение MiniMax §6:119 в этой части фактически неверно. Herder `src/mcp/human-request-tools.ts:102–113` вызывает askHuman и возвращает record/binding; `src/human-request/question-binding.ts:49–57` прямо говорит, что caller затем posts binding в Notice. **Карточку создаёт/доставляет existing `noticeplace_ask_human` → POST `/v1/human-requests`** (`noticeplace/mcp/notify_mcp.py:327–380`). Различать binding → delivered → canonical answer → native continuation. `queued`/`uncertain` не delivered; UUID не ответ. Вступление §2C «human branch exit = delivered request» противоречит верному §6.124: dependency на человеческое решение остаётся pending до canonical answer и применимого действия. Stable request_id сам по себе не делает повторы «невозможными» (§6.123): нужен тот же persisted binding, payload/key и reconciliation accepted/UNKNOWN receipt. Новый сервис для этого не нужен.

**5. Testing — не всегда новый тестовый файл и зелёный runner.** MiniMax §4.98 применим к поручению написать тест. Для «только руками проверь два сценария» достаточно assigned attempts/observations/blocker evidence: assignment complete может иметь product **CHANGES_REQUIRED**. Требовать новый test artifact или product PASS — расширение scope. «Проверь и исправь» остаётся engineering задачей; краткий статус в процессе не заменяет исходную цель. Это два результата, а не лазейка в gate.

## Конечный минимум и критерии начала реализации

Выбранный вариант: **existing outcome + ordered applicable stages с per-type defaults + raw source refs и предметный close + progress-scoped continuation + existing bound Notify seam**. Без universal shell interpreter, нового verdict service, второго quota MCP/runner, новых timers или обещанного OpenCode veto.

Разрешённую реализацию не нужно задерживать ради переименования B/C, исправления пути файла в отчёте или forced consensus. Достаточно принять следующие проверяемые инварианты в patch/tests и не ослаблять их ради GREEN:

1. Echo/wrong target/old revision не закрывают canary; соответствующий реальный API/CLI result имеет достижимый положительный close. Source refs не единственный критерий.
2. Testing с найденным дефектом завершается в своём scope; обязательный merge не снимается N/A; внешний запрещённый main не мутируется; staging push не выдаётся за final delivery.
3. Duplicate/no-progress не rearm; relevant repair даёт одно необходимое продолжение. Live job/UNKNOWN не дублируются, свежий Stop сохраняется через compaction/resume.
4. Binding-only/queued/sent-unanswered не закрывают human decision; canonical answer возвращается в exact native session через существующий idempotent путь. Программная декларация N/A/permission не создаёт полномочий.
5. Реальные ordinary-prompt canaries и установленная candidate поверхность проверяются перед заявлением delivery; OpenCode observer limitations, непокрытые сценарии и незакрытая приёмка остаются явными.

**Residual dissent:** rereadability без semantic соответствия и one-shot на неизменный obligation set я по-прежнему не принимаю как достаточные механизмы. Standalone phone escalation исследованием не доказана: не обещать её из факта доставки карточки и не подменять фиктивным incident; недостающая эскалация ограничивает соответствующую итоговую acceptance, а не независимую реализацию outcome/consumer checks. Остальные crux разобраны за этот раунд; отдельного голосования и нового общего исследования не требуется. Итоговый delivery/quorum verdict остаётся у назначенного coordinator/owner и должен отражать эти ограничения.
