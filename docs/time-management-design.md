# Автоматический учёт времени LHC

Исследование 2026-09-09. Это рекомендация реализации, не заявление о готовой
автоматизации. Текущий 1.2.4 содержит ручной interval CLI и прежние hooks.

## Вывод

Предпочтителен один встроенный таймер с тонкими native-адаптерами. Агент отмечает
начало смысловой задачи и её завершение; hooks обслуживают интервалы без вызовов
модели и без текста в контексте на каждом событии. Человек секундомер не включает.
Это не механизм выбора проекта: владелец задачи определяется из текущей работы.

Два варианта:

- Только hooks: меньше действий агента, но невозможно надёжно отличить новую
  задачу от уточнения, а завершение ответа от завершения бизнеса. Подходит для
  времени сессии, недостаточно для времени задачи.
- Hooks плюс `task_start`/`task_finish`: два смысловых действия агента на задачу,
  общий автоматический таймер между ними. Рекомендуется: сохраняет смысл задачи
  через ответы, ожидания и продолжения без ручного pause/resume после каждого шага.

Первый срез переиспользует существующие lhc_active_time/lhc_time_guard и операции
из установленного пакета. Для переносимого интерфейса инструментов подходит
MCP-компонент того же плагина; отдельный сервер/плагин/демон не нужен. Не строить
MCP-обвязку прежде, чем проверены реальные lifecycle-события трёх клиентов:
имеющийся CLI достаточен для первых canary.

## Почему одной спецификации недостаточно

[Agent Plugins 1.0](https://agent-plugins.org/specification) стандартизирует
skills и MCP; lifecycle hooks относятся к клиентским расширениям. Совпадение
формата пакета не доказывает одинаковую доставку событий.

| Runtime | Что использовать | Что проверено здесь |
|---|---|---|
| Codex | UserPromptSubmit, Stop, Interrupt, SessionEnd; tool/permission events | CLI 0.153.3 экспортирует соответствующие enum в native API schema. Исполнение нового набора событий ещё не проверено. |
| ZCode | UserPromptSubmit, Stop, PermissionRequest, tool events | CLI 0.16.5 загружает LHC 1.2.4, но сообщает unsupported PreCompact/PostCompact; SessionEnd также отклоняет. |
| OpenCode | session.status/idle/error, permission.asked/replied и tool events | CLI 1.18.11; официальный plugin API имеет события. Текущий LHC адаптер обрабатывает chat.message, tool.execute.after и compaction, но не idle. |

Источники: [Codex hook engine](https://github.com/openai/codex/blob/main/codex-rs/hooks/src/engine/mod.rs),
[ZCode hooks](https://zcode.z.ai/en/docs/hooks),
[OpenCode plugins](https://opencode.ai/docs/plugins/).
Локальные доказательства: `.tmp/time-management-schema/` и
`.tmp/time-management-zcode-plugins.json`. Они disposable; существенные выводы выше.

## Семантика измерения

- Wall time задачи: от её фактического начала до завершения, включая ожидания.
- Рабочие интервалы runtime: между подтверждёнными состояниями выполнения и
  остановки. Это не CPU time и не время только генерации модели.
- Ожидания считать отдельно там, где есть обе границы события. Один
  PermissionRequest без надёжного события возобновления не доказывает точную
  длительность ожидания; такой участок помечать неполным.
- Stop закрывает интервал ответа, а не бизнес-задачу. Задача продолжается до
  task_finish после принятого результата. Compaction не сбрасывает часы.
- Повторные события не удваивают время. Перезапуск с незакрытым интервалом
  сохраняет подтверждённое и помечает пробел, не записывает весь простой в работу.
- Каждый worker имеет свои интервалы. Их сумма — усилие; время завершения цели
  считается отдельно по фактической параллельности и зависимостям.

Технические часы живут в штатных plugin data клиента. ToDo и бизнес-записи
остаются в проекте, которым агент занимается; runtime cwd не выбирает его.
Обычный hook пишет состояние и молчит. Сообщение модели требуется при
существенном отклонении, сломанном учёте или положенном checkpoint. Двухчасовой
learning-trigger сохраняет границу наблюдаемости: hook не обещает сработать
посреди единственного долгого вызова, если клиент не предоставляет такого события.

## Приёмка прежде обещания «работает везде»

В каждом установленном runtime выполнить настоящую короткую задачу, задержку
инструмента, ожидание пользователя, продолжение, прерывание и завершение.
Сопоставить события и интервалы; убедиться, что idle не посчитан работой,
следующий ответ не обнулил сумму, а завершение ответа не закрыло задачу.
Если конкретное событие не приходит, отметить незакрытое покрытие и исправить
адаптер; не подменять проверку реального runtime искусственными payload.
